## Problem Statement

ColoredCow's candidate evaluator currently sits in the most crowded slot in developer-hiring technology: "AI reads a GitHub profile, outputs a scored multi-dimensional evaluation + interview questions." Paid competitors already own this: Exiqus (now wound down and open-sourced), Evalo, GotSkillz, GitAnalyze, Grilo, HexcAI, SourceKit, HyreTech, plus an open-source "ATS for GitHub." Shipping this is a good engineering achievement but a bad product position — undifferentiated, fighting incumbents with more polish and pricing.

Prateek Narang (Founder/CEO, ColoredCow) asked for "a product that solves real problem and involves real users." Today the tool has exactly one user: the author. The strategic question is not "add more features" — it is which empty market slot to claim, and how to win over the founder with evidence.

## Landscape Findings

Three-layer reading of the hiring-tech market:
- **Layer 1 (conventional):** Everyone evaluates GitHub → scored report + interview questions. Incumbents: Evalo, GotSkillz, GitAnalyze, Grilo (competitor status varies; each actively sold).
- **Layer 2 (current discourse):** The market is moving AWAY from scores to evidence. Exiqus — the closest sold competitor — wound down and open-sourced with an explicit policy (as documented in its repo): no scores, no ratings, no verdicts; only evidence patterns, with anti-hallucination guards. This validates evidence-first as the direction.
- **Layer 3 (eureka):** Every culture/values-fit tool in the space (Bryq, Fortay, Neuroworx, MyCulture.ai, Talegent, SkillSauce/TESSA) measures fit by SELF-REPORT — questionnaires, value selection, scenario questions, AI interviews. **None derive values-fit from actual GitHub behavior.** GitHub is a goldmine of behavioral evidence of how someone works, and nobody is mapping behavior→values. That intersection is open. The conventional wisdom ("values fit needs a questionnaire") is wrong where skilled candidates' public work already exists.

## Approaches Considered

### Approach A: Lead with Behavioral Values-Fit (the chosen spine)
Reframe the existing 7 dimensions (Code Quality, Technical Judgment, ColValues Alignment, Communication, Problem Complexity, Learning Trajectory, Technical Breadth) as *values evidence*, each backed by citeable GitHub artifacts. The signal→dimension→value mapping the prompt builder must implement:

| Collected signal | Feeds dimensions | ColoredCow value(s) evidenced |
|---|---|---|
| Commit cadence/frequency | Learning Trajectory, Problem Complexity | Always Learning, Take Responsibility |
| README/docs presence + quality | Communication, Technical Breadth | Build Remarkable; Respect and Make Each Other Successful (partial — doc-sharing facet only) |
| CI + tests presence | Code Quality, Technical Judgment | Build Remarkable, Take Responsibility |
| Commit-message length heuristic | Communication, Technical Judgment | Take Responsibility, Always Learning |

Phase-1 coverage status for all six ColoredCow values, so nothing is silently absent: **Take Responsibility** (mapped), **Build Remarkable** (mapped), **Always Learning** (mapped via commit cadence; PR-feedback facet is no-signal in Phase 1), **Respect and Make Each Other Successful** (partial — doc-sharing facet from README/docs; collaboration facets need PR/issue data, no-signal in Phase 1), **Plentiful for Everyone** (no-signal in Phase 1 — needs open-source/community data not collected), **Freedom and Creativity** (no-signal in Phase 1 — "creative/novel/independent decision" signals have no collected proxy). The four mapped/partial values carry the evidence story; the two no-signal values render an explicit disclosure rather than an invented score.

The ColValues dimension becomes the hero, not one of seven. The "evidence-citation layer" is the explicit requirement that every justification and evidence item on `EvaluationDimension` traces to a specific artifact actually fetched — **file path + commit SHA/URL** (only these are in hand today; `GithubService` has no PR/issue endpoints beyond `open_issues_count`). Enforcement lives in `EvaluationStorage`/prompt builder so no dimension can pass validation without either a citable artifact OR the explicit `{"insufficient": true}` marker (E1: a flagged dimension may record an LLM score for display, but that score is excluded from the verdict). **Citation grounding (review decision A2): citations are content-grounded, not existence-only.** The prompt is fed, alongside the selected paths: a README/docs snippet (~40 lines), per-commit message subjects (already in hand via the commit feed), and excerpts of top-N sampled file content — reusing the content `RepositoryAnalyzer` already fetches for line-estimation (`getFileContent`, `RepositoryAnalyzer.php:83-92`) rather than new API calls. The validator must check that the cited artifact SUPPORTS the claim, not merely that the path/commit exists in the fetched set; a citation that passes existence but not support is treated as a failed citation.
- **Effort:** M — but note the citation layer requires feeding artifacts into the prompt: selected file paths (top-N, **default N=10**, ranked by file-tree order with docs/CI/tests present priority and path-depth asc ties — **review decision E2: NOT by most-recent-commit date per file**, because `GithubService::getRepoCommits` returns repo-level commits with only `sha` + `commit.author.date` and no per-file attribution (`GithubService.php:214-228`), so per-file recency is uncomputable without new per-file `path=` API calls; recency-based ranking and its data collection are deferred to Phase 2), files over 200 KB clamped out, plus an in-memory artifact registry to validate model citations against what was actually fetched and capped commit samples (**default 25** — a prompt-side sub-sample of the 100 commits the analyzer fetches; the raw fetch retains each commit's top-level `sha` and `commit.author.date`, which feed both the registry and the recency ranking), plus an in-memory artifact registry to validate model citations against what was actually fetched. Not a free add-on; still M, not S. **Sequencing (review decision D1):** the citation layer is a Phase-1.5 build — after the pilot, never during it. The build order is (1) artifact persistence, then (2) prompt injection, then (3) the validator: persist the registry inputs (top-N selected file paths and the 25 commit samples with their `sha`/`commit.author.date`) onto `RepositoryAnalysis`/`Repository` so the raw fetched artifacts survive `RepositoryAnalyzer` (currently discarded after scoring) and are available to the prompt builder at evaluation time; only then teach `EvaluationPromptBuilder` to feed those artifacts into the prompt; only then build the citation validator/registry check. **One engineering task rides inside step 3's release (review decision A4):** the minimal evidence renderer in `resources/views/candidates/show.blade.php` (currently renders `{{ $item }}` as plain strings, `show.blade.php:277-279`) must ship in the SAME release that introduces `{file_path, commit_sha, url}` objects and the `{"insufficient": true}` marker — otherwise the current UI throws an "array given" error on the first object-backed evaluation. Full report redesign stays Phase 2. This week stays at pilot scope, zero build.
- **Risk:** Low–Med — the two genuinely weak edges are (a) thin portfolios with no citable artifacts (see Success Criteria no-evidence handling) and (b) values with no collected signal (see value-coverage note above). Citation-invalid responses follow a defined policy: **review decision E6 — the validator is a SEPARATE generation-free validation pass** (its own AI call whose sole job is claim-vs-artifact support-checking over the registry excerpt), not a self-attestation inside the generation prompt; re-prompt once with a narrowed artifact list; if still invalid, fall back through the existing AI-provider fallback chain; if both fail, store the dimension with an "insufficient evidence" flag rather than rejecting the whole evaluation. **Review decision E4 — input is size-bounded:** a total prompt-bytes cap (~100 KB default) with deterministic truncation (largest excerpt first) so the built prompt always fits the weakest provider (gpt-4o-mini, ~128k-token context); the artifact selection defaults (N=10 files, 25 commits, 40-line README snippet) are checked against the cap, and if they exceed it the excerpts truncate to the cap before any other adjustment. Path-matching is normalized before validation (strip leading `./`, lowercase, resolve directory prefixes — "directory citation" matches any file in that subtree) so model paraphrases don't false-fail the citation check. **Job timeout (review decision P1):** the ladder's worst case is ~480s (2 providers × 120s `Http::timeout` per pass × 2 passes) vs `EvaluateCandidateJob::$timeout = 300` (`EvaluateCandidateJob.php:24`); a mid-cascade worker kill would interrupt the "flag, never reject" guarantee. Raise the job timeout to 600s when the citation layer ships.
- **Risk:** Low — no new infra; market position is genuinely defensible.
- **Pros:** Only player in "behavior→values"; truthfully differentiates; positions existing code as the moat.
- **Cons:** Requires the author to stop calling it a "score" and start calling it "evidence" — a marketing discipline shift, not a code shift.
- **Reuses:** `EvaluationStorage`, `EvaluationDimension`, prompt builder, radar chart, repositories/repository_analyses schema.

### Approach B: Culture Fingerprint as Product (Phase 2 extension)
Each client defines a "culture fingerprint" — their values, mapped to behavioral indicators — which re-weights the evaluation. Revenue-per-client config instead of one-off tool.
- **Effort:** L for v1 of the config surface, XL for the full multi-tenant engine.
- **Risk:** Med — incumbents (Fortay) already own the "fingerprint" vocabulary; credibility is hard.
- **Pros:** Recurring revenue moat; each company becomes a config, not a fork.
- **Cons:** Heaviest lift; farthest from the founder-evidence wedge; brand collision with Fortay.
- **Reuses:** same dimension/evidence engine, plus a new `culture_configs` store.

### Approach C: Showcase-Piece Engine (framing)
Design the novel behavior→value engine as the artifact that demonstrates the author's skill — documented architecture, adversarial evidence layer, anti-hallucination guards, deterministic tests — readable and browser-facing. Serves the personal-portfolio goal and gives Prateek something demonstrative beyond a demo.
- **Effort:** S (it already exists), or M if produced as a public write-up.
- **Risk:** Low as framing; High if it substitutes for real usage evidence.
- **Pros:** Directly serves "showcase my skill"; builds credibility for B.
- **Cons:** On its own, reads as demo not business.
- **Reuses:** everything.

## Recommended Approach

**Blend: A as the spine, B as the Phase 2 revenue story, C as the framing.** The product is repositioned as "behavioral values-fit evaluation" (A). The fingerprint engine (B) is documented as the natural next phase so the mainstream story exists without building it now. The architecture is designed and presented as a portfolio showcase (C) — which doubles as the evidence Prateek can see when he looks at the code.

Rationale mapped to the founder's ask: this is the only combination that (1) claims ground no incumbent holds, (2) keeps the founder-gate wedge affordable within a week (usage evidence, not a new engine), and (3) makes the author's craft itself part of the value proposition.

3. **Positioning vs. architecture resolved:** "evidence, not scores" is a *marketing and display* commitment, not a schema one. `EvaluationStorage` enforces 1-10 scores and a normalized verdict — that stays. **Review decision A3: verdict normalization is currently DEAD CODE** — `validate(array $parsed)` passes by value and `store()` writes the un-normalized verdict (`EvaluationStorage.php:107-109`, `:20`). Fix the signature/build (by-ref or return+apply) as an implementation task and add a test asserting the stored verdict matches the score map, so the Phase-2 determinism story rests on real enforcement. The change is in the report UI: lead with the cited evidence for each dimension and surface the score/verdict as a derived summary, not the headline; the vendor-neutral story is told in the copy and layout, not the data model. **Citation persistence (clarification):** "no schema migration" applies to the score/verdict model only. Citations are persisted as structured objects `{file_path, commit_sha, url}` inside the existing `evaluation_dimensions.evidence` JSON column — the registry used for in-job validation is in-memory, but the artifacts written to the report come from the persisted `evidence` field, so the report survives the queue job's lifetime with no new table.
4. Who is the named gate-checker at ColoredCow for the pilot's outcomes — HR lead or Prateek directly?
5. Under the tightened evidence model, can citations be drawn from subset-fetched artifacts (top-N files, capped commits) without introducing selection bias that a critical HR reviewer would catch? (Feasibility of the citation layer itself, before committing to the redesign.)

## Success Criteria

**This-week criteria (the pilot):**
- One real ColoredCow HR person evaluates one real candidate end-to-end without coaching, in a documented session, within one week of this plan being accepted. Debrief protocol is fixed in advance: post-session questions (what did you trust / hesitate on / decide) plus the HR user's shortlist decision in their own words. (Pilot.) **Review decision E3A — pilot claims are derated:** the pilot validates the CURRENT scored-UI UX and surfaces blockers only. It does NOT claim to prove values-fit under HR scrutiny — that claim is explicitly positioned behind the Phase-1.5 evidence build, and the founder-facing report says so honestly. (The reframe's hypothesis — a culture-fit verdict from public behavior stands up to HR scrutiny — is first testable in Phase 1.5, not this week.)
- The pilot runs on the **current scored UI** — sequencing is explicit: pilot first on what exists, then redesign the report from pilot blockers. This keeps the week at pilot scope, not M-effort build. The citation layer (Approach A effort bullet) is Phase 1.5, sequenced artifact-persistence → prompt-injection → validator, and explicitly does NOT ship this week. No-evidence handling is decision-only in the pilot: **default selected now is the per-dimension "insufficient evidence" flag** (see JSON shape + score policy below), no scoring or verdict changes. The early-exit "portfolio too thin" state stays a Phase 2 build; whether HR prefers it is captured as a tabletop question during the pilot, not built this week.
- **Insufficient-evidence policy (defined so an engineer can build it without guessing):** the `evidence` JSON column is an array of citation objects `{file_path, commit_sha, url}`; a flagged dimension contains exactly one object `{"insufficient": true}` and no citations. **Review decisions E1 + E5 — flagged scores are EXCLUDED from the verdict and ColValues is weighted+gated.** A flagged dimension's LLM score is recorded for display but excluded from verdict computation; the verdict is derived from evidence-backed dimensions only, with a bare-minimum threshold (verdict requires ≥2 evidence-backed scored dimensions, else the verdict is `insufficient_data` rather than one of the five hire options). ColValues Alignment carries senior weight (2× other dims) when evidence-backed, and a strong verdict (hire/strong_hire) is PROHIBITED when ColValues is flagged. `EvaluationStorage` validation accepts the marker object as a valid evidence entry, so storage rejects nothing. The report renders flagged dimensions de-emphasized with a disclosure line "insufficient evidence: no collected signal for this value" and labels the verdict "provisional" when any flag is present.
- The pilot candidate is **artifact-rich by construction**: it must clear the thin threshold (≥2 repos with authored commits — "authored" = commits whose `author.login` or `commit.author.{name,email}` matches the evaluated profile in the fetched commit log), and at least one repo with tests + CI + README present, so the pilot exercises the evidence path, not the edge case. A contingency candidate is pre-picked in case the chosen candidate fails the threshold at evaluation time.
- Author completes one silent observation session and records hesitations/surprises (addresses Q5's zero-observation gap).
- ColoredCow HR reports the evidence trail is actionable and comparable — measured by the fixed debrief protocol (their words, not a numeric survey).

**Deferred criteria (Phase 2, explicitly out of the pilot's scope):**
- Evaluation consistency poll: same candidate, repeated run, consistent verdict (PRD KPI 2). **Determinism note:** Gemini/OpenAI without fixed sampling can flip on rerun; this work pins temperature/sampling and/or gates the verdict behind a deterministic evidence-aggregation rule (count of evidence-backed signals) rather than raw LLM output.
- Value prop on the report shifts from "score" to "evidence" in the rendered UI (report redesign after pilot blockers surface).
